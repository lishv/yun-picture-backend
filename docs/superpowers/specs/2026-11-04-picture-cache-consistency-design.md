# 图片列表缓存一致性设计

## 目标

在不新增配置、不引入回调或消息机制的前提下，修复图片数据更新或删除后，Caffeine 和 Redis 仍可能返回旧列表数据的问题。

## 现状

图片列表采用 Cache-Aside 读取模式：

1. 优先读取 Caffeine。
2. Caffeine 未命中时读取 Redis，并将 Redis 结果回填 Caffeine。
3. 两级缓存均未命中时查询 MySQL，并将查询结果写入 Redis 和 Caffeine。

列表缓存键由查询条件序列化后计算哈希值生成，当前包含分页列表和游标列表两类缓存。一个图片可能同时存在于多个查询结果中，因此无法根据图片 ID 精确更新某一个列表缓存。

## 设计

继续保留现有查询条件哈希缓存键，不增加图片 ID 缓存和布隆过滤器。

图片更新、编辑、批量编辑、审核或删除成功后，按以下顺序处理：

1. 完成 MySQL 数据修改并成功提交。
2. 删除 Redis 中的图片分页列表和游标列表缓存。
3. 清空当前应用实例中的 Caffeine 图片列表缓存。

数据库操作失败时不清理缓存。

缓存清理逻辑直接写入现有写接口，在数据库操作成功后复用 `PictureController` 中已有的 `StringRedisTemplate` 和 Caffeine 缓存对象完成清理，不额外增加方法。缓存失效失败不增加额外补偿、回调或消息队列逻辑。

## 涉及接口

- 管理员更新图片：`POST /picture/update`
- 用户编辑图片：`POST /picture/edit`
- 批量编辑图片：`POST /picture/edit/batch`
- 管理员审核图片：`POST /picture/review`
- 删除图片：`POST /picture/delete`

图片上传暂不纳入本次修改，因为本次范围是已有图片的更新和删除；后续如要求上传后立即刷新列表，可复用同一缓存清理方法。

## 一致性边界

该方案适用于当前单后端实例部署。Caffeine 是进程内缓存，多实例部署时只能清除处理写请求实例中的本地缓存；其他实例仍可能在本地过期前读取旧数据。多实例场景需要再引入缓存版本或跨实例失效通知，不属于本次最小修改范围。

并发读写期间仍存在 Cache-Aside 的短暂竞争窗口，本次不增加延迟双删、分布式锁等复杂机制。

## 验证

- 更新、编辑、批量编辑和审核成功后，两类 Redis 列表缓存被删除，Caffeine 被清空。
- 删除成功后，两类 Redis 列表缓存被删除，Caffeine 被清空。
- 数据库操作失败时，缓存清理方法不执行。
- 原有列表读取顺序和回填逻辑保持不变。
- 后端相关测试和编译通过。
