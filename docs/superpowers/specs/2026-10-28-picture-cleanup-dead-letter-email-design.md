# 图片清理死信邮件通知设计

## 目标

图片文件经过正常队列和 30 分钟延迟队列两轮清理后仍失败时，由最终死信队列触发一次超级管理员邮件提醒。30 分钟内后续死信不再重复发信，直接确认消费；完整失败数据继续以 `picture_cleanup_task` 表为准。

## 范围

本次只做最小修改：

- 增加 `dlx.picture.queue` 消费逻辑。
- 复用现有 `JavaMailSender` 邮件能力。
- 使用 Redis 控制 30 分钟邮件冷却。
- 增加管理员告警邮箱配置。

不增加通知表、定时任务、通用消息中心、前端页面、第三轮 COS 自动重试或额外停放队列。

## 现有前提

- 延迟队列第二轮消费失败时，系统已经先把 `picture_cleanup_task` 更新为 `FAILED`，并保存最后一次错误。
- 随后消息被拒绝并进入 `dlx.picture.queue`。
- 超级管理员可以在“图片管理 → 文件清理异常”中查询全部 `FAILED` 任务并标记人工处理完成。

因此，死信邮件只负责提醒，不承担失败数据存储。

## 处理流程

死信消费者收到包含 `taskId` 的 `PictureDeleteMessage` 后：

1. 使用 Redis `SETNX` 创建全局冷却键 `picture:cleanup:admin-email:cooldown`，有效期 30 分钟。
2. 如果冷却键已经存在，说明 30 分钟内已经发过告警，消费者正常返回，RabbitMQ 自动 ACK 当前消息。
3. 如果成功创建冷却键，向配置的超级管理员邮箱发送一封图片清理失败提醒。
4. 邮件发送成功后正常返回，RabbitMQ 自动 ACK 当前消息，冷却键保留到自然过期。
5. 邮件发送失败时删除冷却键并抛出异常，使当前消息重新入队，等待后续再次发送。

部署消费者后，已有死信中的第一条触发邮件，其余消息在冷却窗口内被快速 ACK；数据库中的失败任务不受影响。

## 邮件内容

- 收件人：配置项 `picture.cleanup.alert-email`。
- 主题：`【绘灵云告警】图片文件清理任务执行失败`。
- 正文：说明已出现最终清理失败、首次触发的 `taskId`，并提示登录超级管理员后台的“文件清理异常”页面查看和人工处理。

邮件不枚举 30 分钟内的全部任务，因为完整明细已经保存在数据库管理页面中。

## 配置

增加：

```yaml
picture:
  cleanup:
    alert-email: ${PICTURE_CLEANUP_ALERT_EMAIL:2570410870@qq.com}
```

冷却时间固定为 30 分钟，不额外引入配置类。

## 代码边界

- 在现有图片清理监听器中增加最终死信队列监听方法，避免新增无必要的消息子系统。
- 在现有 `EmailManager` 中增加专用的图片清理告警发送方法，复用发件人和 HTML 邮件创建逻辑。
- Redis 冷却判断放在死信消费逻辑中；验证码邮件现有逻辑不改变。

## 确认与异常语义

- 冷却键已存在：正常返回并 ACK。
- 邮件成功：正常返回并 ACK。
- 邮件失败：删除冷却键并抛出异常，不确认消息。
- Redis 操作失败：异常向上抛出，不确认消息。

邮件发送成功后、RabbitMQ ACK 前发生进程中断时，可能重复发送一封邮件。这符合告警场景中“允许极少量重复、不能静默漏报”的取舍。

## 验证

- 首条死信会发送邮件，并创建 30 分钟 Redis 冷却键。
- 冷却期内的后续死信不会发送邮件，并被正常 ACK。
- 冷却键过期后的下一条死信会再次发送邮件。
- 邮件发送异常时冷却键被删除，死信不会被确认。
- 原有正常队列、延迟队列、失败任务查询和人工处理流程保持不变。
